<a name="s5-01"></a>
## S5-01 · 모의 데이터

**Mock Data** · PDF 119쪽

### 뜻·쓰임

개발·시연·테스트에 쓰는 대체 데이터다. 응답을 흉내 내는 모의 서버와는 구별되며, 데이터만 정상이어도 실제 시스템의 지연·오류·경계 상황은 검증되지 않는다.

### 혼동 구분

Mock Data는 대체 데이터이며 mock server는 응답 동작을 흉내 낸다. 데이터 30건만으로 실패·지연이 검증되지는 않는다.

### 실행 명령

```text
고정 seed로 재현 가능한 상품 mock data 30건을 만들고 빈 목록·긴 이름·품절·null 이미지·서버 오류 시나리오를 함께 제공하라.
```

### 설정·계약

실제 계약과 같은 필드명·타입·제약을 사용한다. seed와 생성기 버전을 함께 기록하고 실제 개인정보 대신 합성 값을 쓴다. API 오류는 데이터 객체만이 아니라 상태 코드·지연으로도 모사한다.

### 검수

빈 값·중복 ID·최대 길이·시간대가 UI와 검증 로직에 어떤 영향을 주는지 확인.

### 수정 명령

```text
빈 값·긴 값·지연·실패를 독립 시나리오로 만들고 실제 응답 계약에 맞춰라.
```

<a name="s5-02"></a>
## S5-02 · 타입 안전성

**Type Safety** · PDF 119쪽

### 뜻·쓰임

허용되는 값과 연산의 관계를 타입 체계로 검사해 오류를 줄이는 성질이다. 정적 타입은 실행 전 검사에 도움을 주지만 네트워크에서 온 실제 데이터가 선언대로인지 자동 보증하지는 않는다.

### 혼동 구분

정적 타입과 런타임 입력 검증은 보완 관계다. type assertion은 외부 값의 진실성을 검사하지 않는다.

### 실행 명령

```text
TypeScript strict 설정을 유지하고 API 응답의 도메인 타입을 정의하라. 외부 JSON은 런타임 스키마로 검증하고 불필요한 any를 제거하라.
```

### 설정·계약

타입 단언으로 오류를 덮기보다 값의 범위를 좁힌다. 외부 입력 경계에서 파싱·검증하고 내부에는 신뢰 가능한 타입을 전달한다. nullable·선택 필드·상태별 데이터 차이를 모델링한다.

### 검수

잘못된 응답 타입·누락 필드·null을 주입했을 때 안전하게 실패하며 빌드 검사도 통과하는지 확인.

### 수정 명령

```text
API 응답에 단언을 붙이지 말고 경계에서 실제 데이터를 검증하라.
```

<a name="s5-03"></a>
## S5-03 · 입력 검증

**Input Validation** · PDF 120쪽

### 뜻·쓰임

입력의 형태와 범위가 계약을 충족하는지 확인하는 과정이다. 클라이언트 검증은 빠른 피드백, 서버 검증은 신뢰 경계의 강제에 필요하다. 정제(sanitization), 출력 인코딩, 권한 검사는 별개의 작업이다.

### 혼동 구분

검증은 입력 허용 여부, sanitization은 정제, escaping은 출력 맥락의 인코딩이다. 각각 다른 문제를 다룬다.

### 실행 명령

```text
회원가입 입력을 클라이언트와 서버 양쪽에서 검증하라. 길이·형식·허용값을 명시하고 필드별 오류 코드와 사용자 메시지를 반환하라.
```

### 설정·계약

필수값·길이·범위·허용 형식을 정의하고 국제 문자·공백 처리 정책을 정한다. SQL에는 매개변수화된 질의를 사용한다. 이메일 형식 통과는 실제 주소 소유 확인과 동일하지 않다.

### 검수

빈 값·과도한 길이·예상 밖 타입·경계값과 직접 API 호출에서도 동일 제약이 적용되는지 확인.

### 수정 명령

```text
프런트 오류 표시만 만들지 말고 서버에서도 같은 비즈니스 제약을 강제하라.
```

<a name="s5-04"></a>
## S5-04 · 자동화 테스트

**Automated Testing** · PDF 120쪽

### 뜻·쓰임

예상 동작을 반복 실행 가능한 검사로 표현하는 방식이다. 단위 테스트는 작은 로직, 통합 테스트는 연결된 구성 요소, E2E는 사용자 흐름을 검증한다. 종류보다 검출할 위험과 실행 비용의 균형이 중요하다.

### 혼동 구분

테스트의 가치는 검출할 위험에 있다. 줄 커버리지가 높아도 의미 있는 단언이 없으면 오류를 놓친다.

### 실행 명령

```text
가격 계산은 단위 테스트, 주문 API는 통합 테스트, 결제 완료 흐름은 E2E 테스트로 검증하라. 경계값과 실제 실패 위험에 근거해 사례를 선택하라.
```

### 설정·계약

테스트를 구현 코드의 복사본으로 만들지 않는다. 시간·랜덤·외부 네트워크를 통제하고 의미 있는 결과를 단언한다. 커버리지 비율만을 품질로 삼지 말고 핵심 계약과 회귀를 중심으로 구성한다.

### 검수

의도적으로 넣은 대표 오류를 테스트가 잡는지, 독립 실행과 반복 실행에서 결과가 안정적인지 확인.

### 수정 명령

```text
구현을 복사한 테스트를 줄이고 경계값·실패·외부 계약을 검증하라.
```

<a name="s5-05"></a>
## S5-05 · 회귀 테스트

**Regression Test** · PDF 121쪽

### 뜻·쓰임

수정 후 이전에 되던 기능이나 해결한 문제가 다시 깨지지 않았는지 확인하는 검사다. 버그 수정의 재발 방지와 리팩터링 보호에 쓰인다.

### 혼동 구분

모든 테스트를 무조건 다시 작성하는 것이 아니다. 변경 영향과 과거 실패를 중심으로 범위를 잡는다.

### 실행 명령

```text
중복 주문 버그를 먼저 재현하는 실패 테스트를 만들고 수정 후 통과시켜라. 기존 정상 주문과 재시도 계약도 유지하라.
```

### 설정·계약

재현 조건·원인·최소 데이터·기대 결과를 기록한다. 환경 의존으로 우연히 통과하지 않게 한다.

### 검수

수정 전 실패·수정 후 성공이 확인되고 관련 정상 흐름이 유지되는지 확인.

### 수정 명령

```text
증상 화면만 비교하지 말고 버그를 만든 입력·동시성 조건을 테스트에 담아라.
```

<a name="s5-06"></a>
## S5-06 · 테스트 픽스처

**Test Fixture** · PDF 121쪽

### 뜻·쓰임

테스트 실행에 필요한 데이터·파일·환경·초기 상태를 준비하는 구성이다. 반복 가능성과 테스트 간 독립성을 확보한다.

### 혼동 구분

프로덕션 데이터를 그대로 복제할 필요는 없다. 너무 큰 공통 fixture는 테스트가 무엇에 의존하는지 숨긴다.

### 실행 명령

```text
각 테스트가 필요한 사용자·주문만 만들고 실행 후 정리하라. 시간·랜덤 값을 고정하며 병렬 실행의 ID 충돌을 막아라.
```

### 설정·계약

setup/teardown·트랜잭션 롤백·파일 경로·시드·타임존을 정한다.

### 검수

테스트 순서를 바꾸거나 하나만 실행해도 같은 결과가 나오는지 확인.

### 수정 명령

```text
다른 테스트가 만든 데이터를 기대하지 말고 필요한 상태를 스스로 준비하게 하라.
```

<a name="s5-07"></a>
## S5-07 · 테스트 더블

**Test Double / Stub / Mock / Fake** · PDF 122쪽

### 뜻·쓰임

테스트에서 실제 의존성을 대체하는 구성의 총칭이다. Stub은 응답 제공, Mock은 상호작용 검증, Fake는 단순 동작 구현 문맥으로 흔히 구분한다.

### 혼동 구분

용어 사용은 라이브러리마다 다를 수 있다. 모든 내부 호출을 mock하면 구현 변경에 지나치게 취약해진다.

### 실행 명령

```text
결제 테스트에는 성공·실패 응답 stub을 쓰고 외부 발송 횟수만 필요한 경우 검증하라. 내부 함수 호출 순서는 과도하게 고정하지 마라.
```

### 설정·계약

실제 계약과의 차이를 문서화하고 통합 테스트에서 경계를 별도 확인한다.

### 검수

더블은 통과하지만 실제 API에서 실패하는 차이가 없는지 확인.

### 수정 명령

```text
네트워크를 대체하되 핵심 도메인 로직까지 가짜로 만들어 버리지 마라.
```

## S5-08 · 계약 테스트

**Contract Testing** · PDF 122쪽

### 뜻·쓰임

서비스·모듈 사이의 요청·응답·메시지 약속이 유지되는지 검증하는 테스트다. 독립 배포된 제공자와 소비자의 호환성을 보호한다.

### 혼동 구분

모든 시스템을 켜는 E2E와 다르며 내부 알고리즘 테스트도 아니다. 선택한 계약이 실제 소비 요구를 반영해야 한다.

### 실행 명령

```text
소비자가 사용하는 주문 필드·오류 코드 계약을 제공자 검증에 연결하고 필드 삭제·타입 변경을 배포 전에 탐지하라.
```

### 설정·계약

명세 버전·선택/필수 필드·알 수 없는 필드·호환 변화 정책을 정한다.

### 검수

제공자 변경 시 기존 소비자의 요청과 해석이 계속 유효한지 확인.

### 수정 명령

```text
샘플 JSON 한 개 비교에 그치지 말고 타입·필수·실패 계약을 검증하라.
```

## S5-09 · 정적 분석·린트

**Static Analysis / Linting** · PDF 123쪽

### 뜻·쓰임

코드를 실행하지 않고 문법·타입·패턴·품질 문제를 검사하는 방식이다. 팀 규칙과 일부 결함을 빠르게 확인한다.

### 혼동 구분

포매팅·타입 검사·보안 분석은 범위가 다르며 어느 하나의 통과가 런타임 정확성을 보장하지 않는다.

### 실행 명령

```text
저장소의 기존 lint·format·typecheck 명령을 확인하고 변경 파일의 실제 오류를 해결하라. 규칙을 끄기 전에 원인을 설명하라.
```

### 설정·계약

도구·설정·기준선·경고 처리·생성 파일 제외를 정한다. 전체 코드의 불필요한 포맷 변경은 피한다.

### 검수

검사 결과와 실행 명령이 기록되고 suppress 주석이 문제를 은폐하지 않는지 확인.

### 수정 명령

```text
검사를 통과시키려고 any·ignore를 늘리지 말고 실제 타입·제어 흐름을 수정하라.
```

<a name="s5-10"></a>
## S5-10 · 코드 리뷰

**Code Review** · PDF 123쪽

### 뜻·쓰임

변경의 목적·동작·구조·위험을 다른 관점에서 검토하는 과정이다. AI 작성 코드도 변경 범위와 근거를 검토할 수 있게 제시해야 한다.

### 혼동 구분

스타일 지적만 하는 과정이 아니며 테스트 통과만으로 리뷰를 대체할 수 없다.

### 실행 명령

```text
PR 설명에 해결 문제, 변경 후 동작, 공개 계약 영향, 실제 검증 결과와 남은 제한을 적고 불필요한 변경을 분리하라.
```

### 설정·계약

비교 기준 커밋·파일 범위·중요 위험·우선순위를 명시한다. 추정 문제는 근거와 재현 조건을 연결한다.

### 검수

리뷰어가 왜 필요한 변경인지와 어떻게 검증했는지 코드를 모두 읽기 전에 이해할 수 있는지 확인.

### 수정 명령

```text
작업 일지를 길게 나열하지 말고 사용자 동작·계약·검증 증거를 중심으로 요약하라.
```
