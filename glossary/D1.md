# D1 · UX 구조와 사용자 흐름

[전체 목차](README.md) · [작업별 찾기](TASK_FINDER.md) · [PDF](../book/AI_Integrated_Prompt_Glossary_KO.pdf) · [이용 조건](../LICENSE.md)

> 무엇을 먼저 보여 주고, 사용자가 어떤 순서로 행동하게 할 것인가?

화면을 만들기 전에 사용자 과업을 고정한다. 기능 분류와 화면 목록, 실제 행동 경로를 구별하고 실패 후 재개 경로까지 요구한다. 생성된 흐름은 사용자 조사 결과가 아니라 검증할 설계안으로 취급한다.

**작업 순서:** 과업 정의 → 정보 분류 → 경로 설계 → 화면 구조 → 실패·복구 경로

<a name="d1-01"></a>
## D1-01 · 정보 구조

**Information Architecture (IA)** · PDF 11쪽

### 뜻·쓰임

콘텐츠의 분류·이름·계층·탐색 관계를 설계하는 작업이다. 메뉴를 정리하거나 여러 기능을 하나의 서비스로 묶을 때 쓰며 사용자가 어디에서 무엇을 찾을지 결정한다.

### 혼동 구분

Sitemap은 구조를 표현하는 산출물이고 IA는 그 구조를 결정하는 활동이다. 조직도와 사용자 관점의 분류가 같다고 가정하지 않는다.

### 실행 명령

```text
고객센터 IA를 결제·배송·반품의 사용자 과업으로 구성하라. 각 메뉴의 포함·제외 기준과 중복 콘텐츠의 대표 위치를 표로 제시하라.
```

### 설정·계약

최상위 분류 5개는 검토용 출발점이다. 깊이·항목 수보다 대표 질문을 찾는 경로를 평가하고 전문 조직 용어는 사용자 용어로 바꾼다.

### 검수

배송지 변경·결제 취소·부분 반품 질문마다 출발점에서 답까지 경로가 있는지 검사.

### 수정 명령

```text
같은 문서가 여러 메뉴에 흩어졌다면 원문 위치를 하나로 정하고 관련 링크로 연결하라.
```

<a name="d1-02"></a>
## D1-02 · 사이트맵

**Sitemap** · PDF 11쪽

### 뜻·쓰임

웹사이트의 페이지 계층과 관계를 정리한 목록 또는 도식이다. 화면 범위 산정과 누락 페이지 탐색에 쓰며 사람이 보는 기획 사이트맵과 검색엔진용 XML 사이트맵은 목적이 다르다.

### 혼동 구분

User Flow는 행동 경로, Sitemap은 페이지 구조다. API 경로나 모든 UI 상태를 각각 독립 페이지로 세지 않는다.

### 실행 명령

```text
서비스 사이트맵을 공개·로그인·관리자 영역으로 나누고 각 페이지의 URL, 접근 조건, 상위 페이지, 핵심 목적을 정리하라.
```

### 설정·계약

동적 상세 페이지는 패턴 /products/{id}로 표현한다. canonical·인덱싱 여부는 검색엔진용 산출물을 만들 때 별도 지정한다.

### 검수

사이트맵의 페이지가 실제 라우트와 연결되고 오류·로그인 복귀 페이지가 빠지지 않았는지 확인.

### 수정 명령

```text
정책 없는 페이지를 늘리지 말고 현재 기능 범위에 필요한 경로만 남겨라.
```

<a name="d1-03"></a>
## D1-03 · 사용자 흐름

**User Flow** · PDF 12쪽

### 뜻·쓰임

사용자가 목표를 달성하며 거치는 행동·화면·분기의 순서다. 구매, 가입, 예약처럼 성공과 실패 조건이 있는 과업에 적합하며 화면 예쁘게 꾸미기 전에 논리적 막힘을 드러낸다.

### 혼동 구분

화면 목록과 달리 결정 조건·되돌아가기·재시도까지 표현한다. 서비스 전반의 감정과 접점을 다루는 Journey Map보다 좁다.

### 실행 명령

```text
비회원 구매 흐름을 상품 선택부터 주문 확인까지 작성하라. 품절·결제 실패·주소 오류 분기와 입력값 보존 규칙을 포함하라.
```

### 설정·계약

노드는 행동 또는 상태로 쓰고 분기에는 예/아니오 대신 실제 조건을 붙인다. 성공 종료와 취소 종료를 구별한다.

### 검수

뒤로 가기·재시도에서 중복 주문과 입력 유실이 없는지 시나리오로 따라간다.

### 수정 명령

```text
실패 후 홈으로만 보내지 말고 실패 지점에서 수정·재개할 수 있는 경로를 추가하라.
```

<a name="d1-04"></a>
## D1-04 · 사용자 여정 지도

**User Journey Map** · PDF 12쪽

### 뜻·쓰임

시간에 따른 사용자 목표·행동·접점·어려움을 함께 정리하는 지도다. 앱 밖의 상담·이메일·배송까지 포함하는 경험을 개선할 때 쓴다.

### 혼동 구분

실측 조사와 기획 가설을 구별한다. 감정 곡선을 임의로 그린 것을 실제 고객 증거처럼 보고하지 않는다.

### 실행 명령

```text
구독 해지 여정을 발견·비교·신청·확인 단계로 나누고 행동, 접점, 예상 마찰, 확인할 조사 질문을 표로 작성하라. 가설은 표시하라.
```

### 설정·계약

사용자 유형·목표·시작/종료 시점을 고정한다. 각 문제에 관찰 근거와 검증 방법을 연결해 범위를 통제한다.

### 검수

서비스 내부 프로세스가 아닌 사용자의 행동으로 단계가 쓰였는지, 근거 없는 단정이 있는지 확인.

### 수정 명령

```text
‘불편함’ 같은 추상 표현을 ‘확인 메일이 없어 해지 완료를 판단하지 못함’으로 바꿔라.
```

<a name="d1-05"></a>
## D1-05 · 와이어프레임

**Wireframe** · PDF 13쪽

### 뜻·쓰임

색과 장식보다 정보 구조, 레이아웃, 화면 간 이동을 검토하는 설계 표현이다. 회색 박스만 있는 화면이 아니라 콘텐츠 우선순위와 핵심 상호작용을 검증하는 도구다. 고해상도 목업과 목적이 다르다.

### 혼동 구분

와이어프레임은 구조 검토에, 시각 목업은 색·타이포 검토에, 프로토타입은 조작 검토에 쓴다.

### 실행 명령

```text
Create a low-fidelity wireframe for a booking flow: search, results, details and confirmation; annotate navigation and error states.
```

### 설정·계약

사용자 과업, 화면 목록, 모바일 기준 너비를 먼저 준다. loading/empty/error 상태와 뒤로 가기를 포함한다. 피드백 대상이 구조인지 시각 스타일인지 명시해 수정 범위를 관리한다.

### 검수

예약 같은 핵심 과업을 처음부터 끝까지 수행할 수 있는지, 막다른 화면이 없는지 확인.

### 수정 명령

```text
화면은 있으나 이동이 불명확하면 버튼마다 목적지와 조건을 주석으로 추가하라.
```

<a name="d1-06"></a>
## D1-06 · 인터랙티브 프로토타입

**Interactive Prototype** · PDF 13쪽

### 뜻·쓰임

화면 사이 이동과 상태 변화를 조작해 볼 수 있게 만든 시제품이다. 사용성 평가나 구현 전 행동 합의에 쓰며 실제 서버와 연결되지 않아도 된다.

### 혼동 구분

클릭되는 것과 기능이 구현된 것은 다르다. Mockup은 주로 외형을 보여 주고 프로토타입은 상호작용을 시험한다.

### 실행 명령

```text
예약 프로토타입에서 날짜 선택·인원 변경·예약 확인을 연결하라. 선택값을 화면 간 유지하고 불가능한 날짜의 비활성 상태를 구현하라.
```

### 설정·계약

검증할 과업 3개와 사용 가능한 입력 범위를 정한다. 가짜 응답·데이터 저장 여부를 명시하고 핵심 경로의 충실도를 높인다.

### 검수

사용자 안내 없이 과업을 완료할 수 있는지, 활성처럼 보이지만 반응 없는 요소가 있는지 확인.

### 수정 명령

```text
핫스폿만 덮어 씌우지 말고 선택·오류·완료 상태가 구분되도록 상호작용을 보강하라.
```

<a name="d1-07"></a>
## D1-07 · 점진적 공개

**Progressive Disclosure** · PDF 14쪽

### 뜻·쓰임

처음에는 핵심 정보만 보여 주고 필요할 때 추가 옵션을 드러내는 원칙이다. 복잡한 설정·입력 폼에서 초기 부담을 줄이는 데 사용한다.

### 혼동 구분

필수 조건이나 가격을 숨기는 것과 다르다. 정보의 중요도가 아니라 현재 과업에 필요한 시점을 기준으로 공개한다.

### 실행 명령

```text
검색 폼에 지역·날짜를 먼저 보여 주고 부가 필터는 ‘상세 조건’에서 펼쳐라. 적용 중인 숨은 필터 수와 초기화 동작을 표시하라.
```

### 설정·계약

기본값·펼침 트리거·상태 유지·접기 후 요약을 정한다. 키보드와 스크린리더에서도 열린 상태를 알 수 있게 한다.

### 검수

숨긴 옵션 때문에 결과가 달라졌을 때 사용자가 이유를 이해하고 되돌릴 수 있는지 확인.

### 수정 명령

```text
고급 옵션을 접더라도 적용 상태 배지와 해제 경로는 유지하라.
```

<a name="d1-08"></a>
## D1-08 · 어포던스와 시그니파이어

**Affordance / Signifier** · PDF 14쪽

### 뜻·쓰임

어포던스는 가능한 행동의 관계이고 시그니파이어는 그 행동을 알리는 단서다. UI에서는 버튼 외형·밑줄·손잡이 같은 단서로 조작 가능성을 전달한다.

### 혼동 구분

눌러 보이는 것은 단서이며 실제 클릭 가능성 자체와 같지 않다. 설명 없는 제스처를 사용자가 알아챌 것으로 가정하지 않는다.

### 실행 명령

```text
드래그 가능한 카드에 손잡이와 키보드 이동 버튼을 제공하라. 일반 정보 카드와 클릭 가능한 카드의 스타일을 구별하라.
```

### 설정·계약

기본·hover·focus·disabled 상태의 단서를 정의한다. 터치 환경에는 hover가 없으므로 첫 화면에서 조작 가능성을 전달한다.

### 검수

설명 없이 클릭 대상과 정적 정보를 구별할 수 있는지, 보이는 조작이 실제로 동작하는지 확인.

### 수정 명령

```text
정적 텍스트의 버튼 같은 외형을 줄이고 실제 행동 요소에 일관된 단서를 집중하라.
```

<a name="d1-09"></a>
## D1-09 · 빈 상태

**Empty State** · PDF 15쪽

### 뜻·쓰임

표시할 데이터가 없을 때 보여 주는 화면 상태다. 첫 사용, 검색 결과 없음, 필터로 모두 숨김은 원인이 달라 안내와 다음 행동도 달라야 한다.

### 혼동 구분

로딩·오류와 다르다. 요청 실패를 ‘데이터 없음’으로 표시하면 원인을 감추고 복구 기회를 없앤다.

### 실행 명령

```text
첫 사용에는 ‘첫 프로젝트 만들기’, 검색 결과 없음에는 조건 완화·초기화를 제시하라. 서버 오류는 별도 오류 상태로 처리하라.
```

### 설정·계약

원인, 제목, 설명, 기본 행동, 보조 행동을 상태별로 지정한다. 장식 이미지보다 해결 경로를 우선한다.

### 검수

초기 계정·0건 검색·필터 조합·API 오류를 각각 재현해 올바른 상태가 보이는지 확인.

### 수정 명령

```text
모든 0건 화면에 같은 문구를 쓰지 말고 원인별 행동을 다르게 제공하라.
```

<a name="d1-10"></a>
## D1-10 · 스켈레톤 로딩

**Skeleton Loading** · PDF 15쪽

### 뜻·쓰임

콘텐츠를 기다리는 동안 최종 배치와 비슷한 자리표시자를 보여 주는 패턴이다. 화면 구조를 예상하게 하고 로딩 중 레이아웃 이동을 줄이는 데 쓰인다.

### 혼동 구분

실제 콘텐츠가 아니며 로딩 완료처럼 보여서는 안 된다. 긴 대기에는 진행 안내·실패·재시도도 필요하다.

### 실행 명령

```text
상품 목록 로딩에 이미지와 제목 높이를 유지한 스켈레톤을 제공하라. reduced-motion에서는 반짝임을 멈추고 오류 시 재시도 UI로 전환하라.
```

### 설정·계약

최종 카드 크기와 예약 공간을 맞춘다. 짧은 요청에는 불필요한 깜빡임을 줄이고 보조기기에는 로딩 상태를 알린다.

### 검수

느린 네트워크에서 콘텐츠 점프, 무한 스켈레톤, 중복 읽기와 초점 이동이 없는지 확인.
