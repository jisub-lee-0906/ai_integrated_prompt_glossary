<a name="s7-01"></a>
## S7-01 · 캐시·무효화 (Caching / Invalidation)

**Caching / Invalidation** · PDF 131쪽

### 뜻·쓰임

계산 결과나 응답을 재사용해 지연과 부하를 줄이는 방식이다. 언제 저장하고 언제 갱신·제거할지까지 정해야 정확성을 유지할 수 있다. 브라우저 HTTP 캐시와 앱 내부 캐시는 제어 계층이 다르다.

### 혼동 구분

캐시는 재사용 정책이고 무효화는 변경 전파 계약이다. 개인화 데이터의 경계와 TTL을 함께 정한다.

### 실행 명령

```text
상품 목록은 쿼리별로 캐시하고 수정 성공 시 관련 목록과 상세 캐시를 무효화하라. TTL과 stale 데이터 표시 정책을 문서화하라.
```

### 설정·계약

키에는 필터·페이지·언어 등 결과를 바꾸는 조건을 포함한다. TTL 60초는 예시다. 개인화 데이터는 사용자 경계를 구분하고 HTTP 캐시의 공유 가능 여부와 저장 정책을 별도로 정한다.

### 검수

수정 직후의 오래된 화면, 로그아웃 후 데이터 잔존, 서로 다른 사용자 사이의 캐시 혼선을 확인.

### 수정 명령

```text
수정 후 오래된 값이 보이면 관련 키·목록·상세 캐시를 함께 무효화하라.
```

<a name="s7-02"></a>
## S7-02 · 비동기 처리 (Asynchronous Programming)

**Asynchronous Programming** · PDF 131쪽

### 뜻·쓰임

I/O 같은 대기 작업을 처리하면서 다른 작업을 진행할 수 있게 구성하는 방식이다. async/await 사용만으로 CPU 작업이 자동 병렬화되지는 않는다. 완료 순서가 요청 순서와 다를 수 있다는 점이 핵심이다.

### 혼동 구분

async/await는 CPU 병렬화 보장이 아니다. 응답 순서·취소·타임아웃을 별도로 설계한다.

### 실행 명령

```text
검색 요청에 debounce 300ms를 적용하고 이전 요청을 취소하거나 무시하라. 최신 검색어 결과만 표시하고 로딩·오류 상태를 구현하라.
```

### 설정·계약

타임아웃·취소·동시 실행 한도·실패 전파 정책을 적는다. 독립 요청은 병렬화할 수 있으나 의존 작업은 순서를 지킨다. debounce는 입력을 묶고 throttle은 호출 빈도를 제한한다.

### 검수

느린 이전 요청이 최신 결과를 덮지 않는지, 화면 이탈 후 갱신과 무한 로딩이 없는지 확인.

### 수정 명령

```text
늦은 응답이 최신 화면을 덮지 않도록 취소 또는 요청 ID 검증을 적용하라.
```

<a name="s7-03"></a>
## S7-03 · 예외 처리 (Exception Handling)

**Exception Handling** · PDF 132쪽

### 뜻·쓰임

실행 중 실패를 감지해 복구하거나 의미 있는 오류로 전달하는 구조다. 모든 예외를 잡고 통과하면 성공처럼 보이는 데이터 손상이 생길 수 있다. 예상 가능한 실패와 프로그래밍 오류를 구별해야 한다.

### 혼동 구분

예외를 잡는 것과 복구하는 것은 다르다. 오류를 무시하면 실패가 정상 처리처럼 보일 수 있다.

### 실행 명령

```text
Python CSV 가져오기에 FileNotFoundError와 ValueError를 구분해 처리하라. 사용자 메시지와 진단 로그를 분리하고 예기치 않은 예외는 숨기지 마라.
```

### 설정·계약

좁은 범위에서 구체적 예외를 처리한다. 자원 정리는 with/finally를 활용하고 재시도는 일시적 오류에 한정한다. 재시도 횟수·백오프와 멱등성을 함께 정해 중복 처리를 막는다.

### 검수

파일 없음·잘못된 값·권한 오류를 재현하고 로그의 원인 보존과 자원 해제를 확인.

### 수정 명령

```text
구체적 예외·사용자 안내·진단 로그를 분리하고 예기치 않은 오류는 원인을 보존하라.
```

## S7-04 · 동시성·병렬성 (Concurrency / Parallelism)

**Concurrency / Parallelism** · PDF 132쪽

### 뜻·쓰임

동시성은 여러 작업을 겹쳐 진행하도록 구성하는 성질, 병렬성은 실제 같은 시간에 실행하는 성질이다. I/O 대기와 CPU 계산의 최적화 전략을 구분한다.

### 혼동 구분

스레드·프로세스·async의 효과는 런타임과 작업에 따라 다르다. 무조건 작업 수를 늘리면 메모리·연결 제한을 넘는다.

### 실행 명령

```text
I/O 작업은 제한된 동시성으로, CPU 계산은 적절한 프로세스·실행 자원으로 분리하고 처리량과 p95 지연을 측정하라.
```

### 설정·계약

작업 종류·워커 수·큐·메모리·취소·오류 전파를 정한다.

### 검수

처리량이 개선되면서 응답 지연·리소스 사용·실패율이 악화되지 않는지 확인.

### 수정 명령

```text
async 키워드만 추가하지 말고 실제 병목과 실행 모델을 확인하라.
```

<a name="s7-05"></a>
## S7-05 · 경쟁 상태 (Race Condition)

**Race Condition** · PDF 133쪽

### 뜻·쓰임

작업의 실행 순서·타이밍에 따라 결과가 달라지는 결함이다. 재고·카운터·캐시·파일 갱신 같은 공유 상태에서 발생한다.

### 혼동 구분

같은 요청의 중복과 관련되지만 동일 개념은 아니다. 단일 프로세스도 비동기 인터리빙으로 경쟁이 생길 수 있다.

### 실행 명령

```text
재고 확인과 차감 사이 경쟁을 원자적 갱신 또는 트랜잭션·제약으로 막고 동시 요청 테스트를 작성하라.
```

### 설정·계약

공유 상태·불변식·갱신 경계·잠금 범위를 명시한다. 읽고 나중에 쓰는 패턴을 점검한다.

### 검수

같은 자원을 동시에 갱신해도 음수 재고·갱신 유실·중복 생성이 없는지 확인.

### 수정 명령

```text
버튼 지연으로 숨기지 말고 서버의 원자적 상태 전이를 보장하라.
```

## S7-06 · 뮤텍스·세마포어 (Mutex / Semaphore)

**Mutex / Semaphore** · PDF 133쪽

### 뜻·쓰임

뮤텍스는 공유 구역의 배타 접근, 세마포어는 동시에 허용할 접근 수를 제한하는 동기화 도구다. 공유 자원 보호와 동시 요청 한도에 쓰인다.

### 혼동 구분

프로세스 내부 잠금이 여러 서버의 분산 경쟁까지 막는 것은 아니다. 잠금 종류와 적용 범위를 명시한다.

### 실행 명령

```text
외부 API 호출 동시성을 세마포어로 5개로 제한하고 오류·취소에도 permit을 반환하라. DB 정합성은 저장소 제약으로 보호하라.
```

### 설정·계약

5는 예시다. 획득 대기 시간·해제 보장·잠금 순서·분산 범위를 정한다.

### 검수

예외 후 자원이 영구 점유되지 않고 교착·기아가 생기지 않는지 확인.

### 수정 명령

```text
전역 잠금으로 모든 작업을 막기보다 필요한 자원과 구역만 제한하라.
```

## S7-07 · 작업 큐·백프레셔 (Queue / Backpressure)

**Queue / Backpressure** · PDF 134쪽

### 뜻·쓰임

큐는 작업을 대기·분배하고 백프레셔는 처리 능력을 넘는 입력을 늦추거나 제한하는 제어다. 대량 업로드·메일·영상 처리에 쓰인다.

### 혼동 구분

큐를 무한히 늘리면 장애를 뒤로 미룰 뿐이다. 전달 보장·중복·실패 큐·작업 상태가 필요하다.

### 실행 명령

```text
이미지 처리 요청을 bounded queue에 넣고 용량 초과 시 명확한 응답을 반환하라. 재시도·중복 제거·실패 작업 격리를 설계하라.
```

### 설정·계약

큐 길이·워커 수·최대 시도·가시성 시간·작업 TTL을 정한다.

### 검수

부하 폭증·워커 중단·재전달에서도 메모리와 처리 상태가 통제되는지 확인.

### 수정 명령

```text
무한 메모리 배열 대신 용량 제한과 재처리 계약이 있는 큐를 사용하라.
```

## S7-08 · 타임아웃·재시도·백오프 (Timeout / Retry / Backoff)

**Timeout / Retry / Backoff** · PDF 134쪽

### 뜻·쓰임

대기 상한과 실패 후 다시 시도하는 정책이다. 일시적 네트워크 오류에서 복구하되 무한 대기와 요청 폭증을 막는다.

### 혼동 구분

모든 오류를 재시도하면 안 된다. 비멱등 연산은 중복 효과를 만들 수 있고 여러 계층의 재시도는 곱절로 증가한다.

### 실행 명령

```text
연결·응답·전체 작업 타임아웃을 구분하고 일시적 오류만 제한 횟수로 재시도하라. 지수 백오프에 jitter를 적용하라.
```

### 설정·계약

최대 횟수·총 시간 예산·Retry-After·취소·멱등성·로그를 명시한다.

### 검수

서비스 장애 시 요청 수가 폭증하지 않고 사용자가 최종 실패를 알 수 있는지 확인.

### 수정 명령

```text
try 루프를 무한 반복하지 말고 오류 종류와 전체 시간 예산을 기준으로 멈춰라.
```

## S7-09 · 서킷 브레이커 (Circuit Breaker)

**Circuit Breaker** · PDF 135쪽

### 뜻·쓰임

실패가 반복되는 의존성 호출을 잠시 차단하고 회복 여부를 제한적으로 시험하는 패턴이다. 장애 확산과 자원 고갈을 줄인다.

### 혼동 구분

재시도와 반대 방향의 역할도 한다. 열림 상태에서 무엇을 반환할지 정의하지 않으면 기능이 갑자기 사라진다.

### 실행 명령

```text
결제 상태 조회의 연속 실패가 임계값을 넘으면 회로를 열고 제한적 탐색 요청으로 회복을 확인하라. 사용자에는 현재 확인 불가를 표시하라.
```

### 설정·계약

closed/open/half-open 전이·윈도·임계값·대체 동작·알림을 정한다.

### 검수

의존 서비스 중단·회복에서 요청 차단과 정상 복귀가 반복 진동 없이 동작하는지 확인.

### 수정 명령

```text
실패 횟수만 세지 말고 시간 창과 성공 탐색 조건을 함께 구현하라.
```

## S7-10 · 프로파일링·성능 예산 (Profiling / Performance Budget)

**Profiling / Performance Budget** · PDF 135쪽

### 뜻·쓰임

시간·메모리·I/O 사용의 실제 분포를 측정하고 허용 한계를 정하는 작업이다. 느린 부분을 추정이 아닌 근거로 고치는 데 쓴다.

### 혼동 구분

평균 응답 시간 하나로 사용 경험을 대표할 수 없다. p95·p99와 처리량·오류율·데이터 크기를 함께 본다.

### 실행 명령

```text
대표 데이터와 동시 사용자 조건에서 CPU·DB·네트워크 시간을 측정하고 가장 큰 병목부터 개선하라. 변경 전후 결과를 같은 조건으로 비교하라.
```

### 설정·계약
