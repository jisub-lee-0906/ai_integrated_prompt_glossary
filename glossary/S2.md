<a name="s2-01"></a>
## S2-01 · REST 방식 API (RESTful API)

**RESTful API** · PDF 101쪽

### 뜻·쓰임

리소스 식별과 표현 전달, 무상태성, 일관된 인터페이스 같은 제약을 따르는 API 설계 방식이다. JSON을 HTTP로 주고받는다는 사실만으로 모든 REST 제약을 충족하는 것은 아니다.

### 혼동 구분

REST는 HTTP JSON의 동의어가 아니다. 메서드 의미·리소스·무상태성 등 적용 범위를 명확히 한다.

### 실행 명령

```text
할 일 API를 리소스 중심으로 설계하라. GET /tasks, POST /tasks, GET /tasks/{id}, PATCH /tasks/{id}, DELETE /tasks/{id}와 상태 코드·오류 스키마를 정의하라.
```

### 설정·계약

목록 페이지네이션·필터와 HTTP 의미를 명시한다. PUT은 대상 표현 교체 의미이고 멱등적이다. PATCH는 부분 수정을 표현하지만 일반적으로 멱등성을 보장하지 않는다. 인증 정보는 각 요청에서 해석 가능해야 한다.

### 검수

같은 요청을 반복했을 때의 효과, 없는 리소스, 잘못된 입력, 권한 부족 응답을 확인.

### 수정 명령

```text
동사형 경로를 바꾸는 데 그치지 말고 상태 코드·표현·반복 요청 의미도 정리하라.
```

<a name="s2-02"></a>
## S2-02 · 엔드포인트 (Endpoint)

**Endpoint** · PDF 101쪽

### 뜻·쓰임

클라이언트가 기능이나 리소스에 접근하는 접점이다. API 문서에서는 경로뿐 아니라 HTTP 메서드와 함께 연산을 식별하는 것이 명확하다. 같은 URL에도 GET과 POST는 다른 동작이 될 수 있다.

### 혼동 구분

Endpoint는 보통 메서드와 경로를 함께 식별해야 한다. 같은 경로의 GET과 POST는 다른 연산이다.

### 실행 명령

```text
GET /api/v1/orders/{orderId}의 요청·응답 계약을 작성하라. 경로 변수 형식, 인증, 200/401/403/404 응답과 JSON 예시를 포함하라.
```

### 설정·계약

base URL, 버전, path/query/body/header의 역할을 분리한다. 경로 매개변수와 선택적 쿼리의 필수 여부를 명시하고 시간·숫자·통화의 표현 형식을 맞춘다. 비밀키를 예시 URL에 넣지 않는다.

### 검수

문서의 예시 요청을 실행했을 때 스키마·상태 코드·인증 규칙이 일치하는지 확인.

### 수정 명령

```text
URL만 나열하지 말고 필수 헤더·입력 위치·성공·오류 스키마를 함께 작성하라.
```

<a name="s2-03"></a>
## S2-03 · OpenAPI 계약 (OpenAPI Specification)

**OpenAPI Specification** · PDF 102쪽

### 뜻·쓰임

HTTP API의 경로·연산·스키마·보안 방식을 기계가 읽을 수 있게 기술하는 명세다. 문서·클라이언트 생성·계약 검증의 공통 기준으로 쓴다.

### 혼동 구분

문서를 생성했다고 서버가 계약을 준수하는 것은 아니다. 명세 버전과 도구 지원을 맞춰야 한다.

### 실행 명령

```text
기존 도구가 지원하는 OpenAPI 버전으로 주문 API를 정의하고 요청·응답 예시, 인증, 오류 코드와 스키마 검증을 연결하라.
```

### 설정·계약

nullable·필수·추가 필드·시간 형식·페이지 응답을 명시한다. 비밀값은 예시에 넣지 않는다.

### 검수

명세 유효성과 실제 응답 일치, 생성 클라이언트의 주요 요청을 확인.

### 수정 명령

```text
문서와 서버를 따로 고치지 말고 계약 변경을 검증 단계에 연결하라.
```

<a name="s2-04"></a>
## S2-04 · HTTP 상태 코드 (HTTP Status Code)

**HTTP Status Code** · PDF 102쪽

### 뜻·쓰임

요청 처리 결과를 표준적인 범주로 전달하는 코드다. 클라이언트가 성공·인증 실패·검증 오류·재시도 여부를 판단하게 한다.

### 혼동 구분

응답 본문의 error 문자열만으로 대체하면 HTTP 수준 처리가 왜곡된다. 401과 403의 의미를 구분한다.

### 실행 명령

```text
생성은 201, 본문 없는 삭제 성공은 204, 잘못된 입력·없는 리소스·서버 실패는 합의한 4xx/5xx로 반환하라.
```

### 설정·계약

구체적 코드와 본문 정책을 API 계약에 적는다. 204에 JSON 본문을 기대하지 않게 한다.

### 검수

성공·실패·부분 실패에서 클라이언트가 올바른 상태와 행동을 표시하는지 확인.

### 수정 명령

```text
항상 200으로 반환하지 말고 실제 의미에 맞는 상태 코드를 사용하라.
```

<a name="s2-05"></a>
## S2-05 · 페이지네이션 (Pagination / Cursor)

**Pagination / Cursor** · PDF 103쪽

### 뜻·쓰임

큰 목록을 나누어 조회하는 방식이다. offset/limit와 cursor 방식은 데이터 변화·정렬·성능에서 특성이 다르다.

### 혼동 구분

무한 스크롤은 UI 패턴, pagination은 데이터 분할 계약이다. 커서도 정렬이 불안정하면 누락·중복이 생긴다.

### 실행 명령

```text
주문 목록을 createdAt과 id의 안정적 정렬로 커서 페이지네이션하고 nextCursor·hasMore를 반환하라.
```

### 설정·계약

페이지 크기·상한·정렬 동률·삭제/추가 시 동작을 정의한다. 임의 정렬을 바꾸면 커서 유효성도 다시 판단한다.

### 검수

페이지 사이 삽입·삭제가 있어도 같은 항목이 중복되거나 건너뛰지 않는지 확인.

### 수정 명령

```text
offset만 늘리지 말고 변하는 데이터에 맞는 정렬 키와 커서 계약을 설계하라.
```

<a name="s2-06"></a>
## S2-06 · 멱등성 (Idempotency)

**Idempotency** · PDF 103쪽

### 뜻·쓰임

동일 요청을 반복해도 의도한 최종 효과가 한 번 실행한 것과 같은 성질이다. 재시도·결제·작업 큐의 중복 처리를 제어할 때 중요하다.

### 혼동 구분

응답 본문·코드까지 매번 같아야 한다는 뜻은 아니다. POST도 애플리케이션의 키·저장 정책으로 멱등 처리를 설계할 수 있다.

### 실행 명령

```text
주문 생성에 idempotency key를 받고 동일 키·동일 본문에는 기존 결과를 반환하라. 같은 키의 다른 본문은 충돌로 처리하라.
```

### 설정·계약

키 범위·보존 시간·본문 해시·동시 요청·원자적 저장을 정한다. 프런트 버튼 비활성만으로 대체하지 않는다.

### 검수

응답 유실 후 재시도와 동시 요청에도 주문이 한 번만 생성되는지 확인.

### 수정 명령

```text
중복 ID 검사와 실제 생성 사이 경쟁을 막도록 저장소 제약·트랜잭션을 함께 적용하라.
```

**함께 구분할 용어:** [트랜잭션 / Transaction](S3.md#s3-05) · [격리 수준 / Isolation Level](S3.md#s3-06)

## S2-07 · 웹훅 (Webhook)

**Webhook** · PDF 104쪽

### 뜻·쓰임

특정 사건이 생겼을 때 외부 시스템이 지정 주소로 HTTP 알림을 보내는 방식이다. 결제 완료·배포·문서 변경 등의 비동기 연동에 쓰인다.

### 혼동 구분

클라이언트가 주기적으로 묻는 polling과 다르다. 도착 순서·단일 전달·즉시 전달이 항상 보장되지는 않는다.

### 실행 명령

```text
결제 웹훅의 서명을 원본 본문으로 검증하고 이벤트 ID로 중복 제거하라. 빠르게 수신 확인한 뒤 작업 큐에서 처리하라.
```

### 설정·계약

재전송·순서 역전·시간 허용·비밀 회전·실패 격리 정책을 공급자 계약에 맞춘다.

### 검수

같은 이벤트 재전송과 이전 상태 이벤트의 늦은 도착에도 주문 상태가 깨지지 않는지 확인.

### 수정 명령

```text
웹훅을 신뢰하는 텍스트 입력처럼 처리하지 말고 검증·중복·비동기 경계를 분리하라.
```

<a name="s2-08"></a>
## S2-08 · 웹소켓 (WebSocket)

**WebSocket** · PDF 104쪽

### 뜻·쓰임

연결을 유지하며 양방향 메시지를 주고받는 통신 방식이다. 채팅·협업·실시간 상태 업데이트에 쓰인다.

### 혼동 구분

HTTP 요청을 자주 보내는 polling과 다르다. 연결이 끊겼을 때 메시지 복원·인증 갱신은 별도 설계해야 한다.

### 실행 명령

```text
실시간 알림에 연결·재연결·heartbeat·마지막 수신 ID 기반 복구를 구현하고 중복 메시지를 제거하라.
```

### 설정·계약

연결 수·메시지 크기·속도 제한·인증·백프레셔·순서 보장을 명시한다.

### 검수

네트워크 단절·탭 복귀·서버 재시작 뒤 누락 없이 정상 상태로 돌아오는지 확인.

### 수정 명령

```text
무한 즉시 재연결을 피하고 지수 백오프와 연결 상태 표시를 추가하라.
```

<a name="s2-09"></a>
## S2-09 · 교차 출처 자원 공유 (CORS)

**CORS** · PDF 105쪽

### 뜻·쓰임

브라우저가 다른 출처의 응답을 스크립트에 공개할지 서버 헤더로 판단하는 체계다. 분리된 프런트엔드와 API를 연결할 때 다룬다.

### 혼동 구분

인증·인가나 CSRF 방어 자체가 아니다. curl에서 요청이 된다고 브라우저 CORS가 해결된 것은 아니다.

### 실행 명령

```text
허용할 프런트 출처를 명시하고 credential 요청과 preflight를 처리하라. 출처를 임의 반사하거나 자격 증명과 와일드카드를 섞지 마라.
```

### 설정·계약

scheme·host·port를 출처 단위로 취급한다. 허용 메서드·헤더·Vary 등 캐시 영향도 확인한다.

### 검수

실제 브라우저의 OPTIONS와 본 요청, 허용·비허용 출처를 검사.

### 수정 명령

```text
모든 출처를 열기 전에 실제 필요한 출처와 인증 전달 방식을 확정하라.
```

<a name="s2-10"></a>
## S2-10 · 그래프QL (GraphQL)

**GraphQL** · PDF 105쪽

### 뜻·쓰임

스키마와 질의를 통해 클라이언트가 필요한 필드를 선택하는 API 질의 언어와 실행 방식이다. 여러 관계 데이터를 하나의 요구로 표현할 때 유용하다.

### 혼동 구분

DB 언어 자체가 아니며 REST의 모든 문제를 자동 해결하지 않는다. 필드 권한·질의 비용·N+1은 여전히 관리해야 한다.

### 실행 명령

```text
상품·리뷰 GraphQL 스키마를 정의하고 필드별 인가, 목록 제한, resolver 배치 처리를 설계하라.
```

### 설정·계약

nullable·오류·페이지네이션·복잡도 상한·캐시 정책을 명시한다. 클라이언트 질의를 신뢰해 무제한 실행하지 않는다.

### 검수

과도한 중첩·비허용 필드·빈 값·resolver 오류에서 응답과 비용이 통제되는지 확인.

### 수정 명령

```text
한 endpoint라는 이유로 단순하다고 가정하지 말고 필드별 계약과 실행 비용을 검토하라.
```
