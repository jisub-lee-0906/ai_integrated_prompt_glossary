<a name="s4-01"></a>
## S4-01 · 리팩터링 (Refactoring)

**Refactoring** · PDF 113쪽

### 뜻·쓰임

외부에서 관찰되는 동작을 유지하면서 내부 구조를 개선하는 작업이다. 기능 추가나 버그 수정과 목적이 다르므로 변경 범위를 구분하면 검토가 쉬워진다. 짧은 코드가 항상 더 나은 구조는 아니다.

### 혼동 구분

리팩터링은 외부 동작 유지가 전제다. 기능 추가·버그 수정은 별도 변경으로 드러내야 검토가 쉽다.

### 실행 명령

```text
공개 동작과 함수 시그니처를 유지하면서 주문 계산 코드를 리팩터링하라. 중복을 줄이고 기존 회귀 테스트 결과와 변경 이유를 제시하라.
```

### 설정·계약

유지할 계약·오류 동작·성능 특성을 먼저 적는다. 테스트가 부족하면 중요한 현재 동작을 기록한 뒤 작게 바꾼다. 이름 변경만으로 끝내지 말고 결합도·중복·책임 분리를 평가한다.

### 검수

대표 입력·경계값·오류 입력에서 전후 결과가 같고 공개 API가 유지되는지 확인.

### 수정 명령

```text
전후 입력·출력·오류 계약을 비교하고 변경된 동작을 리팩터링이라는 말로 감추지 마라.
```

<a name="s4-02"></a>
## S4-02 · 모듈화 (Modularization)

**Modularization** · PDF 113쪽

### 뜻·쓰임

코드를 책임과 경계에 따라 나누고 인터페이스로 연결하는 방식이다. 파일을 많이 만드는 것과 다르며, 함께 바뀌는 코드는 모으고 서로 다른 변경 이유는 분리하는 것이 핵심이다.

### 혼동 구분

모듈화는 책임 경계와 의존 계약을 만드는 일이다. 파일 수 증가가 목적은 아니다.

### 실행 명령

```text
결제 흐름을 UI, application service, domain, gateway adapter로 분리하라. 의존 방향과 공개 인터페이스를 설명하고 순환 의존성을 제거하라.
```

### 설정·계약

입출력 계약과 의존 방향을 먼저 쓴다. 작고 단순한 앱에 과도한 계층을 강제하지 않는다. 테스트에서 외부 I/O를 대체할 수 있도록 경계를 두되 비즈니스 규칙이 프레임워크에 묶이지 않게 한다.

### 검수

한 기능의 변경이 관계없는 모듈까지 퍼지지 않는지, 독립 테스트가 가능한지 확인.

### 수정 명령

```text
순환 의존을 확인하고 함께 바뀌는 코드를 모으되 서로 다른 책임을 분리하라.
```

<a name="s4-03"></a>
## S4-03 · 관심사 분리 (Separation of Concerns)

**Separation of Concerns** · PDF 114쪽

### 뜻·쓰임

서로 다른 책임을 독립적으로 이해·변경할 수 있게 나누는 원칙이다. UI·업무 규칙·저장·통신이 한 함수에 섞일 때 정리 기준이 된다.

### 혼동 구분

코드를 무조건 계층별 폴더에 옮기는 것과 다르다. 경계 사이 데이터 계약이 없으면 결합은 그대로다.

### 실행 명령

```text
주문 검증·금액 계산·저장·응답 변환을 역할별로 나누고 순수 계산은 외부 I/O 없이 테스트 가능하게 하라.
```

### 설정·계약

책임별 입력·출력·실패 유형을 정한다. 작은 기능을 위해 과도한 추상 계층을 강제하지 않는다.

### 검수

금액 규칙 변경이 UI·DB 연결 코드를 불필요하게 수정하지 않아도 되는지 확인.

### 수정 명령

```text
긴 함수를 크기만으로 자르지 말고 변경 이유와 의존성을 기준으로 나눠라.
```

<a name="s4-04"></a>
## S4-04 · 의존성 주입 (Dependency Injection)

**Dependency Injection** · PDF 114쪽

### 뜻·쓰임

필요한 외부 기능을 내부에서 직접 생성하지 않고 바깥에서 전달받는 방식이다. 저장소·메일·시간·랜덤 같은 의존성을 교체·테스트하기 쉽게 한다.

### 혼동 구분

항상 전용 DI 프레임워크가 필요한 것은 아니다. 함수 인자·생성자로도 구현할 수 있다.

### 실행 명령

```text
주문 서비스에 payment gateway와 clock을 주입하고 테스트에서는 가짜 구현을 전달하라. 비즈니스 규칙은 공급자 SDK를 직접 호출하지 않게 하라.
```

### 설정·계약

수명·인터페이스·오류 계약·기본 구현을 정한다. 모든 값을 무분별하게 주입하지 않는다.

### 검수

테스트가 실제 네트워크 없이 동작하고 구현 교체 시 서비스 로직이 유지되는지 확인.

### 수정 명령

```text
전역 객체를 몰래 참조하지 말고 실제 사용하는 의존성을 경계에 드러내라.
```

<a name="s4-05"></a>
## S4-05 · 인터페이스·계약 (Interface / Contract)

**Interface / Contract** · PDF 115쪽

### 뜻·쓰임

모듈이 제공·요구하는 동작과 데이터의 약속이다. 함수 시그니처뿐 아니라 오류·부작용·순서·성능 기대도 포함될 수 있다.

### 혼동 구분

타입 선언만으로 런타임 의미가 전부 보장되지는 않는다. 이름이 같은 메서드도 계약이 다르면 대체할 수 없다.

### 실행 명령

```text
Storage 인터페이스에 get/put/delete의 없는 키·덮어쓰기·실패 동작을 명시하고 파일·메모리 구현이 같은 계약 테스트를 통과하게 하라.
```

### 설정·계약

입력 범위·결과·예외·동시성·소유권을 정한다. 구현 세부를 불필요하게 노출하지 않는다.

### 검수

여러 구현을 바꿔도 호출자가 같은 의미로 동작하는지 확인.

### 수정 명령

```text
함수 이름만 맞추지 말고 경계값·오류·부작용까지 동일하게 하라.
```

<a name="s4-06"></a>
## S4-06 · 어댑터 (Adapter)

**Adapter** · PDF 115쪽

### 뜻·쓰임

외부 시스템의 형식·인터페이스를 내부 계약에 맞게 변환하는 경계다. API 공급자·DB·메시지 형식을 교체할 때 핵심 로직을 보호한다.

### 혼동 구분

단순 데이터 복사와 다르며 오류·단위·시간·필드 의미의 변환도 필요하다.

### 실행 명령

```text
결제 공급자의 상태·오류 코드를 내부 PaymentResult로 변환하는 adapter를 작성하고 공급자 고유 필드는 경계 밖으로 새지 않게 하라.
```

### 설정·계약

누락 값·알 수 없는 상태·시간대·금액 단위와 호환 버전을 명시한다.

### 검수

샌드박스 응답·새 필드·알 수 없는 오류에도 안전한 내부 결과를 생성하는지 확인.

### 수정 명령

```text
공급자 응답을 UI까지 그대로 넘기지 말고 내부 도메인 계약으로 변환하라.
```

## S4-07 · MVC·MVVM (MVC / MVVM)

**MVC / MVVM** · PDF 116쪽

### 뜻·쓰임

UI와 상태·동작의 책임을 나누는 아키텍처 계열이다. MVC는 모델·뷰·컨트롤러, MVVM은 모델·뷰·뷰모델의 관계를 중심으로 설명한다.

### 혼동 구분

프레임워크마다 실제 역할이 다르며 이름만 붙였다고 분리가 완성되지 않는다. 모든 웹 앱에 동일 구조를 강제하지 않는다.

### 실행 명령

```text
현재 프레임워크의 관행을 유지하면서 화면 표시 로직과 도메인 규칙을 분리하고 이벤트·상태가 흐르는 방향을 설명하라.
```

### 설정·계약

누가 상태를 소유하고 입력을 처리하는지 구체화한다. 양방향 바인딩의 갱신 루프를 주의한다.

### 검수

뷰 교체나 단위 테스트가 도메인 코드 변경 없이 가능한지 확인.

### 수정 명령

```text
폴더 이름을 MVC로 바꾸는 데 그치지 말고 실제 의존과 호출 경로를 정리하라.
```

## S4-08 · 합성과 상속 (Composition / Inheritance)

**Composition / Inheritance** · PDF 116쪽

### 뜻·쓰임

합성은 다른 객체·기능을 조합하고 상속은 타입 계층의 특성을 물려받는 재사용 방식이다. 기능 변형을 얼마나 독립적으로 다룰지 결정한다.

### 혼동 구분

상속을 무조건 금지하거나 모든 중복을 상속으로 없애는 식의 일괄 처방은 피한다. 대체 가능성과 변경 결합을 평가한다.

### 실행 명령

```text
알림 발송에 채널 전략을 합성해 이메일·푸시를 교체 가능하게 하라. 여러 조건을 상속 계층 조합으로 폭증시키지 마라.
```

### 설정·계약

변하는 축·공통 계약·수명·기본 동작을 정한다. 부모의 내부 구현에 자식이 강하게 의존하지 않게 한다.

### 검수

새 채널을 추가할 때 기존 채널을 수정하거나 조건문을 연쇄 추가하지 않아도 되는지 확인.

### 수정 명령

```text
중복 코드만 보고 상속하지 말고 같은 의미의 타입 관계인지 먼저 판단하라.
```

## S4-09 · 이벤트 기반 구조 (Event-driven Architecture)

**Event-driven Architecture** · PDF 117쪽

### 뜻·쓰임

상태 변화 사건을 발행하고 소비자가 반응하도록 구성하는 방식이다. 작업 분리·비동기 연동에 유용하지만 전달·순서·중복·관측을 설계해야 한다.

### 혼동 구분

명령은 수행 요청, 이벤트는 일어난 사실을 나타낸다. 이벤트 버스 도입만으로 결합이 사라지지 않는다.

### 실행 명령

```text
OrderPlaced 이벤트에 안정적인 ID·발생 시각·스키마 버전을 포함하고 알림 소비자는 중복 처리를 안전하게 하라.
```

### 설정·계약

at-least-once 등 전달 계약·재시도·실패 큐·순서 범위·발행 원자성을 정한다.

### 검수

소비자 장애·중복·순서 역전·이벤트 스키마 변화에서 복구 가능한지 확인.

### 수정 명령

```text
모든 처리를 이벤트로 흩뜨리기 전에 즉시 일관성이 필요한 경계를 확인하라.
```

## S4-10 · 유한 상태 머신 (Finite State Machine (FSM))

**Finite State Machine (FSM)** · PDF 117쪽

### 뜻·쓰임

제한된 상태와 허용된 전이로 동작을 모델링하는 방식이다. 주문·업로드·편집기의 불가능한 상태 조합을 줄이는 데 쓴다.

### 혼동 구분

여러 boolean을 독립적으로 늘리는 방식과 다르다. 상태·이벤트·가드·부작용을 구분한다.

### 실행 명령

```text
업로드를 idle/uploading/success/failure/cancelled로 모델링하고 이벤트별 전이표와 금지 전이를 작성하라.
```

### 설정·계약

동시 이벤트·취소·재시도·복구 시점을 명시한다. 상태에 필요한 데이터 타입도 연결한다.

### 검수

완료 후 progress가 다시 증가하거나 취소된 작업이 성공으로 바뀌지 않는지 확인.

### 수정 명령

```text
isLoading·isSuccess가 동시에 true가 되지 않도록 단일 상태 모델로 정리하라.
```
