<a name="s6-01"></a>
## S6-01 · 인증·인가 (Authentication / Authorization)

**Authentication / Authorization** · PDF 125쪽

### 뜻·쓰임

인증은 ‘누구인가’, 인가는 ‘무엇을 할 수 있는가’를 판단한다. 로그인 여부만 확인하면 다른 사람의 리소스에 접근하는 취약점이 남을 수 있다. 버튼 숨김은 접근 통제가 아니다.

### 혼동 구분

인증은 신원 확인, 인가는 행동 허용 판단이다. 서버는 리소스 소유권까지 확인해야 한다.

### 실행 명령

```text
로그인으로 사용자를 식별한 뒤 서버에서 주문 소유권을 검사하라. 다른 사용자의 주문 ID로 요청하는 경우를 테스트하고 비밀값을 응답에 포함하지 마라.
```

### 설정·계약

세션 수명·로그아웃·권한 모델과 리소스 소유권을 정의한다. 토큰 저장과 쿠키 속성은 위협 모델에 맞춰 결정한다. 사용자 입력의 role이나 userId를 서버 검증 없이 신뢰하지 않는다.

### 검수

미로그인·다른 소유자·권한 회수·만료 세션 상황에서 서버가 일관되게 접근을 거부하는지 확인.

### 수정 명령

```text
다른 사용자의 ID로 직접 요청하는 테스트를 추가하고 버튼 숨김에 의존하지 마라.
```

**함께 구분할 용어:** [입력 검증 / Input Validation](S5.md#s5-03)

<a name="s6-02"></a>
## S6-02 · 환경 변수·비밀값 (Environment Variables / Secrets)

**Environment Variables / Secrets** · PDF 125쪽

### 뜻·쓰임

환경별 설정을 코드와 분리해 전달하는 방법이다. 환경 변수라는 저장 형식 자체가 암호화나 접근 통제를 제공하는 것은 아니다. 빌드 시 브라우저 코드로 치환되는 값은 공개될 수 있다.

### 혼동 구분

환경 변수는 설정 전달 방식이지 암호화 저장소 자체가 아니다. 클라이언트 번들에 들어간 값은 공개될 수 있다.

### 실행 명령

```text
설정값은 환경 변수로 분리하고 .env.example에는 이름과 가짜 예시만 넣어라. 서버 비밀키가 클라이언트 번들에 포함되지 않도록 검사하라.
```

### 설정·계약

필수값은 시작 시 검증하고 누락 시 명확하게 실패하게 한다. 비밀값은 관리 시스템에서 주입하고 로그에 출력하지 않는다. 공개·서버 전용 접두사 규칙은 사용하는 프레임워크 문서를 기준으로 확인한다.

### 검수

저장소·산출물·로그에 실제 키가 없는지, 개발/운영 값이 섞이지 않고 누락 시 실패하는지 확인.

### 수정 명령

```text
비밀값을 서버 경계에 두고 로그·소스맵·산출물에서 노출 여부를 검사하라.
```

<a name="s6-03"></a>
## S6-03 · 세션·토큰 (Session / Token)

**Session / Token** · PDF 126쪽

### 뜻·쓰임

로그인 이후 요청을 사용자와 연결하는 상태·자격 증명 방식이다. 서버 세션 ID 또는 서명된 토큰 등 여러 구성이 있으며 만료·회수·저장 정책이 필요하다.

### 혼동 구분

JWT는 형식이며 암호화된 비밀 저장소의 동의어가 아니다. 서명된 payload는 읽을 수 있는 경우가 일반적이다.

### 실행 명령

```text
세션 만료·로그아웃·회수를 정의하고 쿠키에는 목적에 맞는 HttpOnly·Secure·SameSite 설정을 적용하라. 토큰의 issuer·audience·서명을 검증하라.
```

### 설정·계약

저장 위치·CSRF/XSS 위협·갱신·다중 장치·시간 오차를 고려한다. 프레임워크 기본 보안 기능을 우선한다.

### 검수

만료·회수된 자격 증명과 다른 대상용 토큰이 거부되는지 확인.

### 수정 명령

```text
토큰을 디코딩했다는 이유로 인증하지 말고 서명과 필수 클레임을 검증하라.
```

<a name="s6-04"></a>
## S6-04 · 역할·속성 기반 권한 (RBAC / ABAC)

**RBAC / ABAC** · PDF 126쪽

### 뜻·쓰임

RBAC는 역할, ABAC는 사용자·자원·환경의 속성으로 접근 조건을 결정하는 방식이다. 관리자·소유자·조직 경계를 설계할 때 쓴다.

### 혼동 구분

role 문자열 하나만 확인하면 같은 역할 사이의 타인 자원 접근이 남을 수 있다. 두 방식을 조합할 수 있다.

### 실행 명령

```text
관리자는 같은 조직의 프로젝트만 관리하고 작성자는 본인 초안만 수정하도록 역할과 자원 속성의 정책표를 작성하라.
```

### 설정·계약

행동·리소스·조직·상태·예외를 명시하고 기본 거부 원칙을 적용한다.

### 검수

모든 역할 조합과 타 조직·타 소유자 접근이 정책대로 제한되는지 확인.

### 수정 명령

```text
프런트에서 보낸 role을 신뢰하지 말고 검증된 서버 신원과 자원 속성으로 판단하라.
```

<a name="s6-05"></a>
## S6-05 · 최소 권한 (Least Privilege)

**Least Privilege** · PDF 127쪽

### 뜻·쓰임

주체가 필요한 작업을 수행할 최소한의 권한만 갖도록 제한하는 원칙이다. 앱 계정·CI 토큰·파일·클라우드 접근에 적용한다.

### 혼동 구분

권한을 전부 없애 기능을 깨뜨리는 것과 다르다. 사용 기간·범위·행동을 좁혀야 한다.

### 실행 명령

```text
빌드 작업에는 소스 읽기와 산출물 작성만 허용하고 배포 자격 증명은 배포 단계에만 주입하라.
```

### 설정·계약

자원 범위·읽기/쓰기·기간·회수·감사를 정한다. 공유 관리자 키 대신 역할별 자격 증명을 사용한다.

### 검수

불필요한 삭제·다른 환경 접근이 실제로 거부되며 정상 작업은 수행되는지 확인.

### 수정 명령

```text
오류가 난다고 관리자 권한을 주지 말고 누락된 구체적 권한만 추가하라.
```

<a name="s6-06"></a>
## S6-06 · 크로스사이트 스크립팅 (Cross-site Scripting (XSS))

**Cross-site Scripting (XSS)** · PDF 127쪽

### 뜻·쓰임

신뢰하지 않는 데이터가 브라우저에서 실행 코드로 해석되는 취약점이다. 사용자 콘텐츠·HTML 삽입·DOM 갱신 경계를 다룰 때 중요하다.

### 혼동 구분

입력에서 특정 단어를 지우는 것만으로 해결되지 않는다. HTML·속성·URL·스크립트 맥락마다 처리 방식이 다르다.

### 실행 명령

```text
사용자 댓글은 기본 텍스트로 렌더링하고 허용 HTML이 필요하면 검증된 sanitizer 정책을 적용하라. 위험한 raw HTML 삽입을 제한하라.
```

### 설정·계약

출력 인코딩·안전한 DOM API·URL 허용·CSP를 계층적으로 적용한다.

### 검수

대표 악성 입력이 코드로 실행되지 않고 정상 콘텐츠는 보존되는지 확인.

### 수정 명령

```text
따옴표만 치환하지 말고 실제 출력 맥락의 안전한 렌더링 방식을 사용하라.
```

<a name="s6-07"></a>
## S6-07 · 크로스사이트 요청 위조 (CSRF)

**CSRF** · PDF 128쪽

### 뜻·쓰임

사용자 브라우저가 자동 전달하는 자격 증명을 악용해 원치 않는 상태 변경 요청을 보내게 하는 공격이다. 쿠키 기반 인증의 쓰기 요청에서 검토한다.

### 혼동 구분

CORS와 다르다. CORS는 주로 응답 읽기 통제이며 요청 발생 자체를 모두 막는 장치는 아니다.

### 실행 명령

```text
쿠키 인증의 상태 변경에 프레임워크 CSRF 보호를 적용하고 토큰·Origin 검증·SameSite를 서비스 흐름에 맞게 구성하라.
```

### 설정·계약

GET으로 상태를 바꾸지 않는다. 외부 로그인·임베드 등 교차 사이트 흐름과 호환되는 정책을 검토한다.

### 검수

토큰 없는 외부 유도 요청이 실패하고 정상 폼·로그인 복귀는 유지되는지 확인.

### 수정 명령

```text
CORS만 설정했다고 끝내지 말고 상태 변경 요청의 위조 방어를 별도로 검증하라.
```

## S6-08 · SQL 인젝션 (SQL Injection)

**SQL Injection** · PDF 128쪽

### 뜻·쓰임

입력 데이터가 SQL 명령 구조로 해석되어 의도하지 않은 질의를 실행하는 취약점이다. 검색·정렬·필터·관리 도구에서 경계를 확인한다.

### 혼동 구분

문자열 escape에만 의존하면 DB·문맥 차이를 놓칠 수 있다. 값과 식별자의 처리도 다르다.

### 실행 명령

```text
모든 사용자 값은 parameterized query로 전달하고 정렬 열 이름은 허용 목록에서만 선택하라.
```

### 설정·계약

ORM 사용 시 raw SQL·동적 조건을 점검한다. DB 계정 권한도 필요한 범위로 제한한다.

### 검수

따옴표·예상 밖 타입·정렬 입력이 SQL 구조를 바꾸지 않는지 확인.

### 수정 명령

```text
문자열 연결 질의를 매개변수화하고 열·테이블 이름은 고정 매핑으로 처리하라.
```

<a name="s6-09"></a>
## S6-09 · 서버 측 요청 위조 (SSRF)

**SSRF** · PDF 129쪽

### 뜻·쓰임

서버가 사용자 지정 주소로 요청하면서 내부 서비스·메타데이터 등 의도하지 않은 자원에 접근하는 취약점이다. URL 가져오기·웹훅 테스트·이미지 프록시에서 중요하다.

### 혼동 구분

브라우저 CORS로 서버 요청을 보호할 수 없다. URL 문자열 검사만으로 DNS·리디렉션 위험이 모두 해결되지는 않는다.

### 실행 명령

```text
외부 URL 수집은 허용 프로토콜·대상 정책을 적용하고 리디렉션마다 재검증하라. 내부·로컬 주소 접근을 네트워크 계층에서도 제한하라.
```

### 설정·계약

DNS 해석·재바인딩·포트·응답 크기·타임아웃·프록시 정책을 정한다.

### 검수

리디렉션·IPv6·사설 주소·큰 응답을 포함한 입력이 정책대로 차단되는지 확인.

### 수정 명령

```text
정규식 하나로 끝내지 말고 실제 연결 대상과 네트워크 접근 범위를 제한하라.
```

<a name="s6-10"></a>
## S6-10 · 비밀번호 해싱 (Password Hashing)

**Password Hashing** · PDF 129쪽

### 뜻·쓰임

비밀번호를 검증용 파생값으로 저장하는 처리다. 복호화가 필요한 암호화와 달리 일방향 검증을 목적으로 설계한다.

### 혼동 구분

빠른 일반 해시 한 번과 비밀번호 전용 KDF는 다르다. salt는 사용자마다 달라야 하며 비밀 비밀번호 자체를 로그에 남기지 않는다.

### 실행 명령

```text
검증된 비밀번호 해싱 라이브러리를 사용하고 알고리즘·비용 설정은 현재 보안 지침과 서버 자원에 맞춰 정하라. 성공 로그인 시 재해시 경로를 둬라.
```

### 설정·계약

salt·비용·버전·속도 제한·복구 흐름을 함께 고려한다. 자체 암호 알고리즘을 만들지 않는다.

### 검수

동일 비밀번호의 저장값이 서로 다르고 잘못된 입력·레거시 해시 전환이 안전한지 확인.

### 수정 명령

```text
SHA-256 한 번으로 저장하지 말고 목적에 맞는 해싱 구현과 비용 정책을 적용하라.
```
