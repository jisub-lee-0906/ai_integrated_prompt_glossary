> 데이터의 관계·정합성·조회 성능을 어떤 용어로 요구할 것인가?

정합성은 프런트 버튼이 아니라 저장소 경계에서도 보장해야 한다. 무엇을 현재값으로 유지하고 무엇을 이력으로 보존할지 결정한다. 조회 성능은 실제 데이터와 실행 계획으로 판단한다.

<a name="s3-01"></a>
## S3-01 · 데이터 스키마

**Database Schema** · PDF 107쪽

### 뜻·쓰임

테이블·열·타입·관계·제약으로 데이터 구조를 정의한 것이다. 지속적으로 저장할 사실과 변경 규칙을 명확히 할 때 필요하다.

### 혼동 구분

API 응답 스키마와 같은 구조일 필요는 없다. 화면의 모든 값을 DB에 중복 저장하지 않는다.

### 실행 명령

```text
주문·주문 항목·상품 스키마를 만들고 타입·필수값·금액 표현·생성 시점 스냅샷과 관계를 설명하라.
```

### 설정·계약

통화는 부동소수 오차를 고려해 정밀 타입 또는 최소 단위 정수를 선택한다. 시간대·ID·삭제 규칙을 명시한다.

### 검수

유효하지 않은 상태를 제약으로 막고 과거 주문 금액이 상품 변경으로 바뀌지 않는지 확인.

### 수정 명령

```text
현재 상품 가격을 매번 읽어 과거 주문을 계산하지 말고 주문 당시 사실을 저장하라.
```

<a name="s3-02"></a>
## S3-02 · 기본키·외래키

**Primary Key / Foreign Key** · PDF 107쪽

### 뜻·쓰임

기본키는 행을 식별하고 외래키는 다른 행과의 참조 관계를 강제한다. 중복과 고아 데이터를 줄이는 데 쓰인다.

### 혼동 구분

인덱스와 역할이 다르다. DB에 따라 외래키 선언만으로 참조 열 인덱스가 자동 생성되지 않을 수 있다.

### 실행 명령

```text
주문 항목에 고유 기본키와 주문 외래키를 두고 주문 삭제 시 RESTRICT 또는 CASCADE 중 정책을 명시하라.
```

### 설정·계약

ID 생성 방식·복합키·참조 가능성·삭제/수정 연쇄를 정한다. DB 동작을 확인한다.

### 검수

없는 주문을 참조하거나 중복 식별자가 들어가는 입력을 DB가 거부하는지 확인.

### 수정 명령

```text
앱 코드 검사만 믿지 말고 저장소 수준의 제약을 함께 적용하라.
```

<a name="s3-03"></a>
## S3-03 · 정규화·비정규화

**Normalization / Denormalization** · PDF 108쪽

### 뜻·쓰임

정규화는 중복과 갱신 이상을 줄이도록 관계를 나누고, 비정규화는 조회 등을 위해 일부 중복을 의도적으로 둔다.

### 혼동 구분

테이블 수가 많다고 무조건 정규화가 잘 된 것은 아니다. 비정규화에는 갱신 책임과 일관성 비용이 따른다.

### 실행 명령

```text
고객 연락처의 대표 저장 위치를 하나로 정하고 주문 당시 배송지는 별도 스냅샷으로 저장하는 이유를 설명하라.
```

### 설정·계약

함수 종속과 변경 주기를 확인한다. 읽기 모델·캐시를 추가하면 갱신 시점과 복구 방법을 정한다.

### 검수

한 사실을 수정할 때 일부 복제만 남아 모순되지 않는지 확인.

### 수정 명령

```text
중복을 모두 제거하기 전에 이력이 보존되어야 하는 사실과 현재값을 구분하라.
```

<a name="s3-04"></a>
## S3-04 · 인덱스

**Database Index** · PDF 108쪽

### 뜻·쓰임

조회 조건·정렬을 빠르게 찾기 위한 보조 자료구조다. 읽기 성능을 높일 수 있지만 저장 공간과 쓰기 유지 비용이 든다.

### 혼동 구분

모든 열에 만들수록 좋은 것은 아니다. 복합 인덱스의 열 순서와 연산자·선택도는 실제 질의에 따라 정한다.

### 실행 명령

```text
사용자별 최신 주문 조회를 기준으로 user_id·created_at·id 인덱스를 검토하고 실행 계획과 쓰기 비용을 비교하라.
```

### 설정·계약

DB·인덱스 유형·정렬·범위 조건·데이터 분포를 기록한다. 작은 테스트 데이터만으로 결론내리지 않는다.

### 검수

실행 계획·실제 지연·읽은 행 수가 개선되고 중복 인덱스가 없는지 확인.

### 수정 명령

```text
느린 쿼리에 인덱스를 무작정 추가하지 말고 필터·정렬 패턴과 계획을 먼저 보라.
```

<a name="s3-05"></a>
## S3-05 · 트랜잭션

**Transaction** · PDF 109쪽

### 뜻·쓰임

여러 데이터 변경을 하나의 논리 단위로 다루는 경계다. 주문과 재고 같은 관련 변경의 일부만 반영되는 상태를 막는 데 쓰인다.

### 혼동 구분

외부 결제 API까지 DB 트랜잭션이 자동으로 되돌려 주지는 않는다. 원자성 범위는 실제 자원 경계에 따라 다르다.

### 실행 명령

```text
주문 생성과 재고 차감을 하나의 DB 트랜잭션으로 처리하고 중간 실패 시 모두 되돌려라. 외부 결제는 별도 보상 흐름을 설계하라.
```

### 설정·계약

길이를 짧게 유지하고 외부 대기를 오래 포함하지 않는다. 격리 수준·재시도·잠금 순서를 정한다.

### 검수

중간 예외·동시 주문·프로세스 실패에 불완전한 행과 음수 재고가 남지 않는지 확인.

### 수정 명령

```text
try/except만 추가하지 말고 실제 commit·rollback 경계를 명시하라.
```

<a name="s3-06"></a>
## S3-06 · 격리 수준

**Isolation Level** · PDF 109쪽

### 뜻·쓰임

동시 트랜잭션이 서로의 변경을 어떤 방식으로 보게 할지 정하는 규칙이다. 중복 예약·재고 경쟁 등에서 정합성과 동시성을 조절한다.

### 혼동 구분

Serializable도 충돌이 전혀 없다는 뜻은 아니다. DB는 직렬화 실패를 반환해 재시도를 요구할 수 있다.

### 실행 명령

```text
좌석 예약의 동시 경쟁을 분석하고 선택 DB의 격리 수준·고유 제약·잠금 전략을 조합해 이중 예약을 막아라.
```

### 설정·계약

DB별 Read Committed·Repeatable Read 동작 차이를 확인한다. 실패 시 전체 트랜잭션 재시도 범위를 정한다.

### 검수

동시에 같은 자원을 갱신하는 테스트에서 허용된 결과만 나오는지 확인.

### 수정 명령

```text
격리 수준을 높인 뒤 오류를 무시하지 말고 충돌 재시도와 사용자 응답을 처리하라.
```

<a name="s3-07"></a>
## S3-07 · 데이터 마이그레이션

**Database Migration** · PDF 110쪽

### 뜻·쓰임

스키마와 데이터를 버전별로 변경하는 절차다. 배포 중 구버전·신버전 앱이 함께 동작하는 기간과 기존 데이터의 변환을 관리한다.

### 혼동 구분

테이블을 새로 만드는 코드와 운영 데이터 변경은 위험·절차가 다르다. 모든 변경이 역방향으로 안전하게 되돌려지지는 않는다.

### 실행 명령

```text
새 필드를 nullable로 추가하고 백필·앱 전환 후 제약을 강화하는 단계적 마이그레이션을 작성하라.
```

### 설정·계약

잠금 시간·데이터량·백업·백필 재개·검증·복구 전략을 정한다. 파괴적 삭제는 별도 단계로 분리한다.

### 검수

기존·신규 앱의 호환성과 백필 완료율, 재실행 시 중복·손상이 없는지 확인.

### 수정 명령

```text
열 이름을 즉시 바꾸기보다 호환 가능한 확장·전환·정리 순서를 사용하라.
```

<a name="s3-08"></a>
## S3-08 · ORM

**Object-relational Mapping** · PDF 110쪽

### 뜻·쓰임

객체·모델과 관계형 DB의 조회·변경을 연결하는 계층이다. 생산성을 높일 수 있지만 실제 SQL·트랜잭션 비용을 가리면 성능 문제가 생긴다.

### 혼동 구분

SQL 이해를 대체하지 않는다. 관계 필드를 순회할 때 N+1 질의가 발생할 수 있다.

### 실행 명령

```text
주문과 항목 조회의 실제 SQL 수를 기록하고 eager loading·batch 조회로 N+1을 줄여라. 필요한 열만 선택하라.
```

### 설정·계약

lazy/eager 로딩·세션 수명·트랜잭션·페이지네이션 동작을 확인한다.

### 검수

목록 크기가 늘어도 질의 수가 선형으로 폭증하지 않고 메모리가 통제되는지 확인.

### 수정 명령

```text
모델 속성 접근이 무료라고 가정하지 말고 발생하는 SQL과 실행 횟수를 검사하라.
```

<a name="s3-09"></a>
## S3-09 · 소프트 삭제

**Soft Delete** · PDF 111쪽

### 뜻·쓰임

행을 물리 삭제하지 않고 삭제 시각·상태로 비활성화하는 방식이다. 복구·감사·참조 관계 유지가 필요할 때 사용한다.

### 혼동 구분

백업이나 법적 보존 정책 자체를 대신하지 않는다. 숨긴 데이터가 검색·집계·고유 제약에 계속 영향을 줄 수 있다.

### 실행 명령

```text
deleted_at 기반 삭제를 구현하고 일반 조회·검색·통계에서 제외하라. 복구 시 고유값 충돌과 실제 영구 삭제 정책을 정의하라.
```

### 설정·계약

접근 권한·복구 기간·인덱스·관계 데이터·저장 비용을 정한다.

### 검수

삭제 후 직접 ID 조회·검색 결과·캐시에서 데이터가 노출되지 않는지 확인.

### 수정 명령

```text
화면에서만 숨기지 말고 서버의 모든 읽기 경로에 삭제 정책을 적용하라.
```

<a name="s3-10"></a>
## S3-10 · 실행 계획

**Query Plan / EXPLAIN** · PDF 111쪽

### 뜻·쓰임

DB가 질의를 수행할 접근·조인·정렬 방법을 보여 주는 정보다. 병목이 인덱스 부재인지 대량 정렬인지 판단하는 데 쓴다.

### 혼동 구분

추정 계획과 실제 실행 측정은 다르다. EXPLAIN ANALYZE는 DB에 따라 실제 질의를 수행하므로 쓰기 질의에 주의한다.

### 실행 명령

```text
느린 조회의 계획과 실제 행 수·시간을 비교하고 큰 추정 오차·전체 스캔·디스크 정렬의 원인을 정리하라.
```

### 설정·계약

대표 데이터량·분포·통계 갱신·캐시 상태를 기록한다. 운영 부하를 고려해 측정 범위를 정한다.

### 검수

변경 전후 p95 지연과 행 수가 개선되며 결과가 동일한지 확인.

### 수정 명령

```text
한 번 빨라진 결과만 보고 승인하지 말고 같은 조건에서 실행 계획과 반복 측정을 비교하라.
```
