<a name="s8-01"></a>
## S8-01 · 지속적 통합·전달·배포 (CI/CD)

**CI/CD** · PDF 137쪽

### 뜻·쓰임

CI는 변경을 자주 통합하고 자동 검사로 문제를 발견하는 과정이다. CD는 배포 가능한 상태를 유지하는 Continuous Delivery 또는 운영 반영까지 자동화하는 Continuous Deployment를 뜻하므로 어느 의미인지 지정해야 한다.

### 혼동 구분

CI와 Delivery와 Deployment를 구분한다. 자동 검증이 운영 자동 반영 권한까지 뜻하지는 않는다.

### 실행 명령

```text
PR마다 lint·타입 검사·테스트·빌드를 실행하는 CI를 구성하라. 성공한 동일 산출물을 스테이징에 배포하고 운영은 명시적 승인 단계와 롤백 절차를 둬라.
```

### 설정·계약

트리거, 실행 환경, 캐시 키, 비밀값 주입, 산출물 보존 기간을 정한다. ‘CI/CD를 구축’만으로 운영 자동 배포 권한을 가정하지 않는다. 검증한 산출물과 배포한 산출물의 식별자를 연결한다.

### 검수

검사 실패 시 다음 단계가 막히는지, 비밀값이 로그에 노출되지 않는지, 이전 버전 복구가 가능한지 확인.

### 수정 명령

```text
트리거·승인·환경·동일 산출물 승격·복구 단계를 명시하라.
```

<a name="s8-02"></a>
## S8-02 · 빌드 (Build)

**Build** · PDF 137쪽

### 뜻·쓰임

소스와 자원을 실행·배포 가능한 형태로 변환하는 과정이다. 컴파일·번들링·최적화·정적 생성 등이 포함될 수 있다. 개발 서버 시작, 의존성 설치, 테스트, 배포와는 각각 다른 단계다.

### 혼동 구분

Build는 산출물 변환, Deploy는 실행 환경에 반영하는 일이다. 개발 서버 동작과 production build 성공도 다르다.

### 실행 명령

```text
저장소의 기존 package manager와 lockfile을 유지해 production build를 실행하고, 실행 명령·산출물 위치·실패 원인을 보고하라.
```

### 설정·계약

런타임 버전, lockfile, 환경 변수와 빌드 모드를 명시한다. Python 프로젝트도 wheel 등 패키지 빌드가 가능하다. 빌드 성공만으로 실제 런타임 동작이나 외부 서비스 연결을 보장하지 않는다.

### 검수

깨끗한 환경에서 재현되는지 확인하고, 산출물을 실제 방식으로 실행해 핵심 화면·경로를 점검.

### 수정 명령

```text
실제 산출물을 서비스 방식으로 실행하고 필요한 환경 변수와 경로를 점검하라.
```

<a name="s8-03"></a>
## S8-03 · 관측 가능성 (Observability)

**Observability** · PDF 138쪽

### 뜻·쓰임

시스템이 내보내는 신호를 통해 내부 상태와 장애 원인을 추론할 수 있는 성질이다. 로그는 사건, 메트릭은 집계 추세, 트레이스는 요청의 경로·시간을 파악하는 데 도움을 준다.

### 혼동 구분

로그·메트릭·트레이스는 서로 보완한다. 수집량보다 장애 원인을 따라갈 수 있는 연결성이 중요하다.

### 실행 명령

```text
주문 흐름에 구조화 로그, 오류율·지연 메트릭, trace ID를 추가하라. 개인정보는 제외하고 대시보드에서 실패 요청을 추적할 수 있게 하라.
```

### 설정·계약

서비스·환경·버전·상관 ID를 일관되게 기록한다. 사용자 ID처럼 값 종류가 많은 필드를 메트릭 라벨로 남발하지 않는다. 수집률·보존 기간·경보 임계값은 서비스 목표와 비용에 맞춘다.

### 검수

사용자 오류 한 건을 관련 서비스까지 추적할 수 있는지, 경보가 실제 조치 가능한 정보를 주는지 확인.

### 수정 명령

```text
버전·요청 상관 ID를 연결하고 개인정보와 과도한 메트릭 라벨을 제거하라.
```

<a name="s8-04"></a>
## S8-04 · 브랜치·머지·충돌 (Branch / Merge / Conflict)

**Branch / Merge / Conflict** · PDF 138쪽

### 뜻·쓰임

브랜치는 변경 흐름, 머지는 서로 다른 변경의 결합, 충돌은 자동 결합이 어려운 부분이다. 병렬 개발과 검토 가능한 이력을 관리한다.

### 혼동 구분

충돌 마커만 없애면 해결된 것이 아니다. 두 변경의 의도·계약을 함께 보존해야 한다.

### 실행 명령

```text
작업 브랜치의 기준 커밋과 변경 범위를 확인하고 충돌은 양쪽 의도를 읽어 해결하라. 결합 후 관련 동작을 검증하라.
```

### 설정·계약

미커밋 변경·대상 브랜치·전략·금지된 이력 변경을 확인한다. 사용자의 작업을 덮어쓰지 않는다.

### 검수

충돌 표시가 없고 양쪽 기능과 테스트가 함께 유지되는지 확인.

### 수정 명령

```text
한쪽 파일을 통째로 선택하기 전에 겹친 변경의 목적과 영향 범위를 비교하라.
```

## S8-05 · 의존성 고정·락파일 (Dependency Pinning / Lockfile)

**Dependency Pinning / Lockfile** · PDF 139쪽

### 뜻·쓰임

설치할 패키지 버전과 해석 결과를 고정해 환경 차이를 줄이는 방식이다. 빌드 재현성과 공급망 검토의 기반이다.

### 혼동 구분

최상위 버전만 적는 것과 전체 의존 해석 고정은 다르다. lockfile도 런타임·운영체제·외부 서비스 차이를 모두 없애지는 못한다.

### 실행 명령

```text
기존 패키지 매니저와 lockfile을 유지하고 재현 가능한 설치 명령을 사용하라. 의존성 변경은 필요한 항목만 수행하고 이유를 기록하라.
```

### 설정·계약

런타임·패키지 매니저·레지스트리·플랫폼을 명시한다. 여러 매니저의 lockfile을 임의 혼합하지 않는다.

### 검수

깨끗한 환경에서 설치·빌드가 동일하게 동작하고 의도치 않은 대규모 업데이트가 없는지 확인.

### 수정 명령

```text
설치 오류를 해결하려고 lockfile을 바로 삭제하지 말고 환경·버전 불일치를 먼저 확인하라.
```

## S8-06 · 컨테이너 이미지·컨테이너 (Container Image / Container)

**Container Image / Container** · PDF 139쪽

### 뜻·쓰임

이미지는 실행에 필요한 파일·설정을 담은 패키지이고 컨테이너는 그 이미지의 실행 인스턴스다. 배포 환경의 일관성을 높인다.

### 혼동 구분

가상 머신과 동일하지 않으며 이미지 자체에 실행 중 데이터가 자동 영속 저장되는 것은 아니다.

### 실행 명령

```text
최소한의 실행 의존성만 가진 이미지를 빌드하고 비밀값은 런타임에 주입하라. 쓰기 데이터는 명시한 외부 저장소·볼륨에 둬라.
```

### 설정·계약

기반 이미지·사용자·포트·healthcheck·리소스·digest를 기록한다. 태그는 바뀔 수 있음을 고려한다.

### 검수

새 컨테이너로 교체해도 필요한 데이터가 유지되고 비밀이 이미지 계층에 남지 않는지 확인.

### 수정 명령

```text
로컬 컨테이너 수정을 운영 원본으로 삼지 말고 재빌드 가능한 선언 파일을 수정하라.
```

## S8-07 · 리버스 프록시·로드밸런서 (Reverse Proxy / Load Balancer)

**Reverse Proxy / Load Balancer** · PDF 140쪽

### 뜻·쓰임

리버스 프록시는 서버 앞에서 요청을 중계하고 로드밸런서는 여러 대상에 분배한다. TLS 종료·경로 연결·부하 분산을 설계한다.

### 혼동 구분

같은 제품이 두 역할을 할 수 있지만 목적은 다르다. 프록시가 있으면 앱의 원래 클라이언트·프로토콜 해석을 맞춰야 한다.

### 실행 명령

```text
/api는 백엔드로 전달하고 정적 파일은 별도 캐시하라. 신뢰할 프록시 범위를 정하고 전달 헤더를 임의 사용자 입력으로 신뢰하지 마라.
```

### 설정·계약

타임아웃·업로드 제한·WebSocket·세션·헬스체크·TLS를 정한다.

### 검수

경로·큰 업로드·실시간 연결·서버 장애 전환이 의도대로 동작하는지 확인.

### 수정 명령

```text
502를 앱 코드 문제로 단정하지 말고 프록시 경로·시간 제한·대상 상태를 순서대로 확인하라.
```

## S8-08 · 헬스체크·레디니스 (Health Check / Readiness)

**Health Check / Readiness** · PDF 140쪽

### 뜻·쓰임

프로세스가 살아 있는지와 실제 요청을 받을 준비가 되었는지 판단하는 검사다. 재시작·트래픽 투입 결정을 구분할 때 쓴다.

### 혼동 구분

Liveness와 readiness를 같은 무거운 DB 검사로 구성하면 외부 장애 때 모든 앱이 재시작될 수 있다.

### 실행 명령

```text
liveness는 프로세스 상태, readiness는 필수 준비 상태로 분리하고 배포 시 준비 완료 전 트래픽을 받지 않게 하라.
```

### 설정·계약

주기·시간 제한·실패 횟수·시작 유예·종료 드레이닝을 정한다.

### 검수

시작 지연·DB 일시 장애·종료 중에 요청 유실과 재시작 폭주가 없는지 확인.

### 수정 명령

```text
모든 의존성 실패를 프로세스 사망으로 취급하지 말고 준비 상태와 복구 행동을 분리하라.
```

## S8-09 · 롤백·점진 배포 (Rollback / Canary / Blue-green)

**Rollback / Canary / Blue-green** · PDF 141쪽

### 뜻·쓰임

롤백은 이전 상태로 복귀, canary는 일부 트래픽부터 검증, blue-green은 두 환경 사이 전환을 활용하는 배포 방식이다.

### 혼동 구분

코드 롤백이 DB·외부 부작용까지 자동 복구하는 것은 아니다. 복구 가능성은 사전 호환 설계에 달린다.

### 실행 명령

```text
새 버전을 제한 트래픽에 배포하고 오류율·지연·핵심 거래 지표가 기준을 넘으면 이전 산출물로 복귀하라.
```

### 설정·계약

관찰 창·판정 지표·트래픽 비율·DB 호환·세션·자동/수동 전환을 정한다.

### 검수

실패 배포를 재현해 실제 복귀 시간과 데이터 정합성을 확인.

### 수정 명령

```text
배포 후 복구를 생각하지 말고 이전 버전과 함께 동작 가능한 변경 순서를 설계하라.
```

<a name="s8-10"></a>
## S8-10 · 기능 플래그 (Feature Flag)

**Feature Flag** · PDF 141쪽

### 뜻·쓰임

코드 배포와 기능 노출을 분리해 대상·환경별로 켜고 끄는 제어다. 점진 출시·실험·긴급 비활성화에 쓰인다.

### 혼동 구분

숨김 UI는 보안 권한 검사를 대체하지 않는다. 오래된 플래그는 복잡도와 테스트 조합을 늘린다.

### 실행 명령

```text
새 검색을 직원 계정부터 켜고 장애 시 즉시 끌 수 있게 하라. on/off 양쪽의 데이터·UI 호환성을 테스트하고 제거 일정을 적어라.
```

### 설정·계약
